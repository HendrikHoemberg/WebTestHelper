# WebTestHelper Plan 11 — The Switcher and the Buttons

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the two interaction checks that navigate but never write. `LANGUAGE_SWITCHER` clicks
each language link and asserts §7.2's three conditions — the URL changed **and** `<html lang>`
changed **and** the visible text actually differs. `BUTTON_REACHABILITY` clicks the controls the
crawl cannot see and asserts that something happens.

**Architecture:** both ride plan 10's machinery unchanged — no new SPI, no migration, no new
property, no UI change. Both follow one rule (D83): **the page script harvests, Java decides.**
The DOM is read in a single `evaluate` that returns plain records and tags the elements it saw;
every rule worth arguing about — which link is a language switch, which button must never be
clicked, what counts as a real change — is a pure Java function with a `-Pfast` test.

**Tech Stack:** Java 25, Spring Boot 4.1.1, PostgreSQL 17 via Testcontainers, Playwright/Chromium
1.62.0, Thymeleaf, HTMX. **No new dependency.**

**Spec:** `docs/superpowers/specs/2026-08-21-webtesthelper-design.md`; §-references point there.
**Roadmap:** `2026-08-27-webtesthelper-phase-3-roadmap.md` — plan 11 of 13. Its deviation index
(D72–D77), plan 10's (D78–D82), the Phase-1 table (D1–D37), plans 6–9's (D38–D71), `CLAUDE.md`'s
plan calibration and `CLAUDE.md`'s test rules all apply and are **not** restated.

**Ends with:** a colleague opens a site whose *English* page has never actually been translated.
The report says: *"Hinter der Sprachwahl „English“ steht auf /en/ derselbe Text wie auf der
Ausgangsseite. Die Übersetzung fehlt."* — with the screenshot of the English page showing German.
One of §1's seven manual checks stops being manual.

**Two browser test classes**, `LanguageSwitcherCheckTest` and `ButtonReachabilityCheckTest`, each
driving Chromium once per class, plus one acceptance test. Candidate selection, the never-click
vocabulary and the three-condition verdict are pure functions and run under `-Pfast`.

## Measurements taken before this plan was written

The roadmap held two open questions for plan 11 and required both to be answered by measurement
rather than by taste. Both were measured against real Chromium on 2026-08-27, on the fixture, with
the project's own `SimHash`. **These numbers are the part of this document that cannot be
regenerated by reading the code.**

### Question 1 — what Hamming distance means *"the visible text actually differs"*?

`document.body.innerText` through `SimHash.of`, 64-bit, word trigrams:

| Pair | Distance |
|---|---|
| fixture `/` (German) ↔ `/en/index.html` | **35** |
| a German page ↔ its **real English translation** (same layout, ~45 words each) | **34** |
| a German page ↔ the same German text served under `/en/` with `lang="en"` | **0** |
| a German page ↔ a **half-translated** copy (nav and heading English, body still German) | **7** |
| two unrelated short German pages (`kontakt.html` ↔ `leistungen.html`) | 24 |
| any page ↔ itself | 0 |

**Chosen: ≤ 12 means the text did not really change** (`maxTextDistance`, per-site overridable via
`CheckConfig.option`). The gap between a real translation (34) and an untranslated copy (0) is
enormous, so the threshold is not delicate; what fixes it inside that gap is the half-translated
case at 7. A page whose navigation is translated and whose body is not **is the failure** — it is
what a half-finished CMS translation looks like — so the cutoff must sit above 7, and 12 does.

It is deliberately **below** plan 3a's soft-404 cutoff of 16, and the two must not be unified: the
soft-404 question is *"is this the same page?"*, this one is *"was any translating done?"*, and the
cost of being wrong runs the other way. A false positive here is a report against a site that is
correctly translated, which §8 says is the one thing that destroys trust. Below 12, a genuinely
translated page would have to be almost entirely shared boilerplate before it tripped.

**The guard that goes with it:** below **20 words** the content condition is not judged at all,
and only the URL and `lang` conditions apply. `SimHash.of` falls back to hashing the whole string
below three words, and the fixture's 19-character `/en/index.html` shows how little text a real
page can carry; two short strings collide at an arbitrary distance in both directions.

### Question 2 — what counts as *"a visible DOM change"*, and does the fixture have a healthy case?

It did not. `index.html`'s `#tut-nichts` was the only case, and a check with only a failing fixture
cannot demonstrate that it stays quiet on healthy markup. A candidate page was built and probed;
the digest is a hash of `document.documentElement.outerHTML` plus `body.innerText.length`,
`body.scrollHeight` and the paused-state of every `<video>`/`<audio>`:

| Control | Navigated | DOM digest changed | Verdict |
|---|---|---|---|
| `<button>` toggling a class on a panel (accordion) | no | **yes** | healthy |
| `<button>` doing `location.href = …` | **yes** | yes | healthy |
| `<a href="#">` setting `open` on a `<dialog>` | no | **yes** | healthy |
| `<button id="tut-nichts">` with no handler | no | no | **dead** |
| `<a href="#">` with no handler | *raw URL says yes* | no | **dead** |

**The trap, and it is the reason this table exists.** Clicking `<a href="#">` leaves
`page.url()` as `…/knoepfe.html#`. A raw string comparison therefore reports *"it navigated"* and
every dead anchor on the web passes the check. Both checks in this plan compare
`UrlNormalizer.normalize(page.url())`, which drops the fragment (`UrlNormalizerNormalisationTest.
dropsTheFragment`), never the raw string.

**Restlessness is real and detectable.** A page with a `setInterval` writing a timestamp changes
its digest across a 500 ms idle window with no click at all. On such a page every dead button
looks alive, so the check reads the digest twice before clicking anything and **abstains from the
whole page** when they differ (D86). 500 ms is also the settle wait after each click: every healthy
case above was observed at it.

**The exclusions were proved by absence.** The probe page's *"Bestellung löschen"* button issues a
`fetch('/verboten-geklickt')` and its `<form>` posts to `/formular`; after a full pass over the page
both request counters were **0**.

## Deviations this plan introduces

D72–D77 are the roadmap's and D78–D82 are plan 10's; both carry their reasoning there.

- **D83 — the page script harvests, Java decides.** Every DOM read in this plan is one `evaluate`
  returning plain records, and every judgement is a pure Java function over them. Plan 10's
  `cookie-banner.js` put its heuristic *in the page* and bought a browser test for every rule it
  contains. The rules here are worth more scrutiny than that — one of them is a list of labels the
  system must never click on a customer's website — and a rule that can only be tested by launching
  Chromium is a rule that gets tested once. §5.1 wanted this module logic-dense and unit-testable;
  D72 gave that up for the four interaction checks, and this gives back everything that does not
  strictly need the browser.
- **D84 — the third condition is a SimHash distance of ≤ 12**, measured above, not derived. It is
  `maxTextDistance` and per-site overridable, because a customer running a two-language site whose
  pages are 80 % shared boilerplate is exactly the case that needs a lower number.
- **D85 — `BUTTON_REACHABILITY` never clicks three classes of control**, and the omissions are the
  check, not a limitation of it: anything inside a `<form>` (plan 12 owns forms, and a submit has
  a side effect on a customer), any `<a>` whose href resolves somewhere other than the current page
  (`DEAD_LINK` already resolves those every run, and a second finding on the same subject is
  duplicate noise), and any label in the never-click vocabulary. What is left is precisely what the
  crawl cannot see: buttons and href-less anchors driven by JavaScript.
- **D86 — `CheckAbstainedException`: "I could not judge" is a third answer, distinct from "nothing
  is wrong".** A check that returns an empty list is telling coverage it looked and saw nothing,
  which lets the run resolve last week's findings on that page (§6.4). A restless page means the
  check could not look. The runner already excludes a throwing check's type from `drivenTypes`
  (D79), so an abstain costs one class and one `catch` clause — and without it the honest outcome
  is unreachable, because the only alternative is a lie in one direction or the other.
- **D87 — `LANGUAGE_SWITCHER` ships on at `ERROR`; `BUTTON_REACHABILITY` ships off at `WARN`.**
  Broken language switching is one of §1's seven manual checks and §11.1 notifies on `ERROR` only,
  so a `WARN` would mean the product quietly stops reporting something it was built to catch. A
  dead button is on neither §1's list nor the customer's critical path, and this is the only check
  in the catalog that clicks arbitrary controls on a live customer site; its false-positive profile
  has never been measured against anything but the fixture. It joins `CONSOLE_ERRORS` and
  `SITEMAP_CONSISTENCY` in `NOISY_BY_DEFAULT`, is offered by guided setup with a sentence saying
  what it does (§13.4), and flips to on when a month of real runs says it is quiet.
- **D88 — an interaction check must leave the page on the URL it was handed.** The runner
  screenshots after evaluation so the evidence shows the state complained about; a check that
  navigated and did not come back attaches a picture of a different page. Stated in the SPI javadoc
  and asserted in both browser tests.

## Decided constants

| Constant | Value | Why |
|---|---|---|
| `maxTextDistance` | 12 | Measured. See D84 and the table above |
| minimum words to judge content | 20 | Below it `SimHash` is hashing a whole short string, not shingling it |
| `maxLocales` per page | 3 | One finding per broken locale, and D75 forbids promoting any of them site-wide. Three is enough to tell *"this locale"* from *"the whole switcher"* |
| `maxButtons` per page | 10 | At ~0.5 s settle plus an occasional navigation this is a few seconds against plan 10's 30 s per-check timeout. A page with forty buttons gets its first ten, deterministically ordered |
| settle wait after a click | 500 ms | Measured: the accordion, the navigation and the `<dialog>` were all visible at it |
| restlessness probe | two digests, 500 ms apart, before the first click | Measured: the `setInterval` page trips it, the static page does not |

**No configuration properties are added.** All four numbers reach a check through
`CheckConfig.option`, which is the per-site channel `RedirectChainCheck.maxHops` already uses.

### Task 1: `LanguageSwitchers` — which links are a language switch, and what counts as a real one

The whole judgement half of `LANGUAGE_SWITCHER`, with no browser anywhere near it. Both halves are
in one class because they are one decision split in two: selection decides what gets clicked, the
verdict decides what the click proved, and a reviewer cannot sensibly accept one and reject the
other.

**Files:**
- Create: `checks/LanguageSwitchers.java`
- Test: `checks/LanguageSwitchersTest.java`

**Interfaces (produces):**

```java
public record LocaleLink(int index, String href, String hreflang, String label, boolean visible) {}
public record LocaleTarget(int index, NormalizedUrl url, String label) {}
public record Observation(NormalizedUrl url, String htmlLang, String text) {}
public enum SwitchVerdict { OK, NO_NAVIGATION, LANG_UNCHANGED, SAME_CONTENT }
```

- `static List<LocaleTarget> select(List<LocaleLink> harvested, NormalizedUrl current, String currentLang, int max)`
- `static SwitchVerdict verdict(Observation before, Observation after, int maxTextDistance)`

**Selection**, in order. Rules 3 and 4 are the ones with teeth:

1. Drop invisible links.
2. Keep a link that **looks like a language switch**: non-blank `hreflang`, **or** a label of at
   most 24 characters matching the vocabulary below (case- and accent-insensitively, whole label
   only — *"Deutschland"* is not *"Deutsch"*), **or** an href whose first path segment is a
   two-letter code or which carries a `lang`, `hl` or `locale` query parameter.
3. Resolve the href against `current` through `UrlNormalizer.resolve`; drop what does not resolve
   and drop targets that are not `sameSiteAs(current)`. A switcher to a partner domain is not this
   site's switcher.
4. Drop the **active locale's own link** — target equals `current` **and** (`hreflang` names
   `currentLang`, or the label's language equals `currentLang`). Everything else that resolves to
   `current` is **kept**, because that is the dead switcher and dropping it by the same rule would
   make `NO_NAVIGATION` unreachable forever.
5. Dedupe by target URL keeping the lowest index, sort by `NormalizedUrl.value()` (D74's stability
   requirement — the same page must produce the same targets in the same order next week),
   truncate to `max`.

The vocabulary. It is the rule, so it is written out rather than described:

```java
private static final Map<String, String> LANGUAGE_WORDS = Map.ofEntries(
        entry("deutsch", "de"), entry("german", "de"), entry("de", "de"),
        entry("english", "en"), entry("englisch", "en"), entry("en", "en"),
        entry("francais", "fr"), entry("franzosisch", "fr"), entry("fr", "fr"),
        entry("italiano", "it"), entry("italienisch", "it"), entry("it", "it"),
        entry("espanol", "es"), entry("spanisch", "es"), entry("es", "es"),
        entry("nederlands", "nl"), entry("niederlandisch", "nl"), entry("nl", "nl"),
        entry("polski", "pl"), entry("polnisch", "pl"), entry("pl", "pl"));
```

Keys are already folded — lowercase, diacritics stripped — and the lookup folds the label the same
way, so `Français` and `FRANCAIS` both hit `francais`.

**Verdict**, first failure wins, and the order is load-bearing: a page that did not navigate has
no meaningful `lang` or text to compare, and a page whose `lang` never changed is untranslated
whatever its text says.

1. `after.url` equals `before.url` → `NO_NAVIGATION`. Both are already-normalised `NormalizedUrl`s,
   which is where the fragment went.
2. `after.htmlLang` is blank, or equals `before.htmlLang` ignoring case → `LANG_UNCHANGED`.
3. Either text has fewer than 20 words → `OK` (not judged, per the measurement section).
   Otherwise `SimHash.hammingDistance` of the two texts `<= maxTextDistance` → `SAME_CONTENT`.
4. Otherwise `OK`.

- [ ] **Step 1: Write the failing test.** `LanguageSwitchersTest`, hand-built records, no browser
      and no Postgres. Selection: an `hreflang` link is a candidate; a plain *"Startseite"* link is
      not; *"Deutschland"* is not (whole-label matching, the rule most likely to be written as
      `contains`); `Français` and `FRANCAIS` both are; a cross-site `hreflang` link is dropped; the
      **self-link whose hreflang is the current lang is dropped**; a self-link labelled *"English"*
      on a German page is **kept**; two links to the same target yield one target; a shuffled input
      yields the same list in the same order (D74); `max` truncates after sorting, not before.
      Verdict: each of the four values, one case each, plus `NO_NAVIGATION` winning over a page
      that would also have failed condition 2, plus the 20-word guard returning `OK` for two short
      unequal texts, plus the boundary — distance 12 is `SAME_CONTENT` and 13 is `OK`.

- [ ] **Step 2: Run it and watch it fail** — `./mvnw test -Pfast -Dtest=LanguageSwitchersTest`.

- [ ] **Step 3: Implement.** Fold labels with `java.text.Normalizer.Form.NFD` and strip combining
      marks; that is what makes one vocabulary entry cover `Français` and `Francais` without
      listing both.

- [ ] **Step 4: Run the suite** — `./mvnw test -Pfast`.

- [ ] **Step 5: Commit.**

```bash
git commit -am "feat(checks): decide what a language switch is, and what proves it worked"
```

### Task 2: `LanguageSwitcherCheck` — click each locale, and the German that makes it a finding

D77's single commit, now with a fourth member: the enum constant, the class, the registry line, the
three explanation keys, the three finding keys, the setup proposal and the help topic land together
or the build is red. Between Step 4 and Step 7 it is red by design.

**Files:**
- Create: `checks/LanguageSwitcherCheck.java`, `src/main/resources/checks/locale-links.js`,
  `src/main/resources/help/sprachumschalter.md`
- Create (fixture): `src/test/resources/fixture-site/interaktiv/sprachen.html`,
  `sprachen-kaputt.html`, `en/sprachen.html`, `en/sprachen-kaputt.html`, `fr/sprachen.html`
- Modify: `model/CheckType.java`, `checks/CheckRegistry.java`, `checks/InteractionCheck.java`
  (javadoc only — D88), `runner/SetupProposals.java`, `src/main/resources/messages.properties`
- Test: `checks/LanguageSwitcherCheckTest.java` — **`@Tag("browser")`**, one Chromium per class

**Interfaces (consumes):** `LanguageSwitchers.select/verdict`, `InteractionTargets.homepage`,
`CheckConfig.option`.

**Interfaces (produces):** `LanguageSwitcherCheck implements InteractionCheck` — `type()` =
`LANGUAGE_SWITCHER`, `defaultSeverity()` = `ERROR` (D87), `messageKeys()` = the three
`finding.LANGUAGE_SWITCHER.*` keys below, `targets(...)` = `InteractionTargets.homepage(...)`.
A switcher is one site-wide artefact of one CMS configuration; driving it on three pages produces
three findings about one missing translation.

The harvest. One `evaluate`, tagging as it goes so Java can click by index afterwards:

```js
// checks/locale-links.js — harvest every anchor; Java decides which are a language switch (D83).
return [...document.querySelectorAll('a')].slice(0, 300).map((a, i) => {
  a.setAttribute('data-wth-locale', String(i));
  const r = a.getBoundingClientRect();
  return {index: i, href: a.href || '', hreflang: a.getAttribute('hreflang') || '',
          label: (a.getAttribute('aria-label') || a.textContent || '').trim().slice(0, 40),
          visible: r.width > 0 && r.height > 0};
});
```

`a.href` is the browser's own resolution, so a relative href and a `#` href both arrive absolute —
and `…/seite.html#` normalises to `…/seite.html`, which is what turns the measured fragment trap
into a `NO_NAVIGATION` finding instead of a pass.

**The drive loop:**

1. Observe the baseline: normalised `page.url()`, `document.documentElement.lang`,
   `document.body.innerText`.
2. Harvest, then `select(..., config.option("maxLocales", 3))`.
3. For each target: click `[data-wth-locale="<index>"]`, wait for the load state, observe again,
   take the verdict, and emit a finding for anything but `OK`.
4. **Restore between candidates**: navigate back to the baseline URL and re-run the harvest. The
   tags do not survive a navigation, and the script assigns indices in document order, so the same
   page re-tags identically. The last restore is also D88's obligation to the screenshot.
5. `subjectKey` is the target URL's `value()` — one broken locale is one finding, week after week.
   **`observedOn` is the baseline URL, never the target.** The finding is about the switcher on the
   page the runner drove, and D74 resolves interaction findings only against the pages actually
   driven; an `observedOn` pointing at `/en/` would be a finding on a page this check never
   drove and could therefore never resolve.

The German copy. §13.2 wants three things above the technical evidence, and the third is the one
that turns a finding into an assignable task.

| Key | Text |
|---|---|
| `check.LANGUAGE_SWITCHER.title` | Sprachumschalter |
| `check.LANGUAGE_SWITCHER.description` | Prüft, ob die Sprachwahl wirklich in die andere Sprache führt: Adresse, Sprachkennzeichnung und der sichtbare Text müssen sich ändern. |
| `check.LANGUAGE_SWITCHER.remediation` | Die Sprachwahl selbst anklicken und die Zielseite ansehen. Steht dort derselbe Text, fehlt die Übersetzung im Redaktionssystem; bleibt die Adresse gleich, ist gar kein Ziel hinterlegt. |
| `finding.LANGUAGE_SWITCHER.noNavigation` | Die Sprachwahl „{0}“ führt nirgendwohin — die Adresse der Seite bleibt dieselbe. |
| `finding.LANGUAGE_SWITCHER.langUnchanged` | Die Seite {0} hinter der Sprachwahl „{1}“ ist weiterhin als „{2}“ ausgezeichnet. |
| `finding.LANGUAGE_SWITCHER.sameContent` | Hinter der Sprachwahl „{0}“ steht auf {1} derselbe Text wie auf der Ausgangsseite. Die Übersetzung fehlt. |

`SetupProposals` gets `conditional(CheckType.LANGUAGE_SWITCHER, evidence.reachable() &&
evidence.languages().size() > 1, REASON_LANGUAGES, …)` — the same signal and the same existing

### Task 3: `Clickables` — the list of things this system will never click

The safety half of `BUTTON_REACHABILITY`, pure and `-Pfast`. It exists as its own task because it
is the only code in the project whose bug is *"the checker bought something on a customer's
website"*, and a rule of that kind must be testable without launching a browser (D83).

**Files:**
- Create: `checks/Clickables.java`
- Test: `checks/ClickablesTest.java`

**Interfaces (produces):**

```java
public record Clickable(int index, String tag, String type, String label, String href,
                        boolean inForm, boolean disabled, boolean visible, String target) {}
```

- `static List<Clickable> select(List<Clickable> harvested, NormalizedUrl current, int max)`

**The rules**, each dropping candidates, in this order:

1. Not `visible`, or `disabled` → drop.
2. `inForm`, or `type` is `submit` or `reset` → drop. Forms belong to plan 12, and a submit has a
   side effect on a customer (D85).
3. `target` is `_blank` → drop. A popup is a second page the check cannot reason about.
4. `tag` is `a` **and** its href resolves through `UrlNormalizer.resolve(current, href)` to
   something other than `current` → drop; `DEAD_LINK` owns those. An `a` with no href, with `#`,
   with a `javascript:` href, or resolving back to `current` is **kept** — that is the JavaScript
   control the crawl cannot see.
5. The folded label contains a never-click token → drop.
6. The folded label matches `CookieBanner`'s accept vocabulary, or *"Nur notwendige"* /
   *"Ablehnen"* → drop. Consent was established by the runner before this check ran; a second
   consent widget is not a broken button.
7. Dedupe by `(label, index)`, sort by `index` — document order, which is stable across runs for
   an unchanged page — and truncate to `max`.

The never-click vocabulary. Substring matching on a folded label, deliberately broad: a false
*exclusion* costs one unreported dead button, a false *inclusion* costs a customer a deleted order.

```java
private static final List<String> NEVER_CLICK = List.of(
        "loschen", "entfernen", "delete", "remove", "leeren", "zurucksetzen",
        "abmelden", "logout", "anmelden", "login", "registrieren", "abbestellen", "kundigen",
        "bestellen", "kaufen", "zahlungspflichtig", "warenkorb", "bezahlen",
        "absenden", "abschicken", "senden", "submit", "download", "herunterladen", "drucken");
```

*"drucken"* is in the list for a mechanical reason as well as a courteous one: `window.print()`
opens a modal the automation cannot dismiss, and the session stops responding.

### Task 4: The third answer — a check that could not judge the page

D86, on its own, before anything needs it. It ships with a fake check and no production caller,
which is deliberate and has a precedent: plan 10's Task 1 shipped the `InteractionCheck` SPI with
an empty registry list and a local fake in the test. The reason to separate it is that a reviewer
can accept *"the runner learns a third answer"* and still reject the button-clicking heuristic in
Task 5 — and the coverage consequence is the one thing in this plan that, if wrong, corrupts data
silently rather than failing a test.

**Files:**
- Create: `checks/CheckAbstainedException.java`
- Modify: `runner/InteractionRunner.java`
- Test: `runner/InteractionRunnerTest.java` (modify)

**Interfaces (produces):**
- `CheckAbstainedException extends RuntimeException`, carrying the `CheckType`, the URL and a
  reason. Its javadoc is where D86 lives: this is **not** `CheckEvaluationException`, whose javadoc
  says a throwing check is a bug and should fail the run loudly. This says the page could not be
  judged, which is a fact about the page and not about the code.
- `InteractionRunner` catches it **ahead of** `catch (RuntimeException)`: log at `INFO` with the run
  id, the check type, the URL and the reason, and leave the type out of that target's
  `drivenTypes`. Mechanically that is the same coverage consequence D79 already produces for a
  thrown exception — reached deliberately, at a log level that does not cry wolf, instead of by
  disguising an abstention as a crash.

Why it cannot be an empty finding list: a check that returns `List.of()` is telling coverage it
looked and saw nothing, and §6.4 then lets the run resolve last week's findings on that page. An
abstention that returned empty would mark a page clean on the strength of never having read it.

- [ ] **Step 1: Write the failing test.** In `InteractionRunnerTest`, a local fake
      `InteractionCheck` that throws `CheckAbstainedException`: the call succeeds, the outcome
      carries no finding, and its type is **absent** from `drivenTypes` while remaining present in
      `candidateTypes` — the second half matters as much as the first, because a type missing from
      the candidates would fall back into the crawl-scoped resolve (plan 10, Finding 5). Keep the
      existing fake that throws a plain `RuntimeException` beside it; the two differ only in log
      level, and the test should say so.

- [ ] **Step 2: Run it and watch it fail** — `./mvnw test -Dtest=InteractionRunnerTest`.

- [ ] **Step 3: Implement.** One class, one `catch` clause ahead of the existing one.

- [ ] **Step 4: Run the full suite** — `./mvnw test`.

- [ ] **Step 5: Commit.**

```bash
git commit -am "feat(checks,runner): a check that cannot judge a page says so"
```

**Interfaces (consumes):** `Clickables.select`, `InteractionTargets.keyPagesOrHomepage`,

**Interfaces (produces):**
- `ButtonReachabilityCheck implements InteractionCheck` — `type()` = `BUTTON_REACHABILITY`,
  `defaultSeverity()` = `WARN`, `messageKeys()` = `Set.of("finding.BUTTON_REACHABILITY.dead")`,
  `targets(...)` = `InteractionTargets.keyPagesOrHomepage(snapshots, site, maxTargets)` — its first
  caller, and the reason plan 10 built it.

The two scripts. The digest is the definition of *"a visible DOM change"*, measured above:

```js
// checks/dom-digest.js — one string that changes when anything a visitor could notice changes.
const s = document.documentElement.outerHTML;
let h = 0;
for (let i = 0; i < s.length; i++) { h = (h * 31 + s.charCodeAt(i)) | 0; }
const media = [...document.querySelectorAll('video,audio')].map(m => m.paused ? '0' : '1').join('');
return h + ':' + s.length + ':' + document.body.innerText.length + ':'
         + document.body.scrollHeight + ':' + media;
```

`outerHTML` catches a class toggle, an inline style, an opened `<dialog>`; `innerText.length` and
`scrollHeight` catch a change rendered inside a shadow root, which `outerHTML` never shows; the
media list catches a play button, which changes no markup at all and would otherwise be the
check's most embarrassing false positive.

```js
// checks/clickables.js — harvest every control; Java decides which may be clicked (D83, D85).
return [...document.querySelectorAll('button, a, [role=button], input[type=button], input[type=submit]')]
  .slice(0, 200).map((el, i) => {
    el.setAttribute('data-wth-btn', String(i));
    const r = el.getBoundingClientRect();
    return {index: i, tag: el.tagName.toLowerCase(), type: el.getAttribute('type') || '',
            label: (el.getAttribute('aria-label') || el.value || el.textContent || '').trim().slice(0, 60),
            href: el.getAttribute('href') || '', inForm: !!el.closest('form'),
            disabled: !!el.disabled, visible: r.width > 0 && r.height > 0,
            target: el.getAttribute('target') || ''};
  });
```

**The drive loop:**

1. Harvest, `select(..., config.option("maxButtons", 10))`. No candidates → return empty. That is
   *"nothing here is broken"*, not an abstain: a page with no buttons has no dead ones.
2. **Restlessness probe**, once, before any click: read the digest, wait 500 ms, read it again.
   Different → throw `CheckAbstainedException`. On a page that rewrites itself every tick, every
   button looks alive and the check would report nothing while claiming it had looked.
3. For each candidate: register a dialog handler that dismisses and records, and a popup handler
   that records; read the current URL and digest **fresh** (an earlier click may legitimately have
   left an accordion open); click `[data-wth-btn="<index>"]`; wait 500 ms; read both again.
4. An effect is: the **normalised** URL changed, or the digest changed, or a dialog appeared, or a
   popup opened. None of the four → one finding, `subjectKey` = the label when non-blank, else
   `tag#index`; `observedOn` = the target URL the runner handed over.
5. Only navigate back when the URL actually changed — and then re-harvest, because the tags are
   gone. Ten candidates on a static page therefore cost ten clicks and no navigations.
6. Leave the page on its target URL before returning (D88).

## Deliberately not in this plan

- **`CONTACT_FORM`.** Plan 12, and D85's exclusion of everything inside a `<form>` is what keeps
  this plan's clicking away from it. `InteractionTargets.withForm` stays unused for one more plan.
- **The credential store.** Plan 13. Nothing here reads a secret.
- **A `<select>`-based language switcher.** `LANGUAGE_SWITCHER` drives anchors only. A
  `<select onchange>` switcher is common enough to be worth having and needs a different driving
  primitive (`selectOption`, then a navigation wait with no element to click), plus its own fixture
  page. It is one task in a later plan, not a widening of this one — and the check's silence on
  such a site is honest silence, not a wrong answer.
- **Language switching inside an iframe.** `CookieBanner` searches child frames because two of the
  three common German CMPs render there. No language switcher does.
- **Re-verifying either check.** D78 and the roadmap's reasoning, unchanged: the retries live inside
  the check, in the context it already holds.
- **Promoting either check's findings site-wide.** D75. A switcher driven on one page and buttons
  on three cannot disprove *"on 312 pages"*.
- **Turning `BUTTON_REACHABILITY` on by default.** D87 states what would change the answer: a month
  of real runs across the customer sites, with the false-positive rate counted. Flipping it is a
  one-line change to `NOISY_BY_DEFAULT` and one line in `SetupProposals`.
- **Any UI work.** The run detail coverage line, the finding detail screen and the check settings
  screen are all generic over `CheckType` and need no edit. If one turns out not to be, that is a
  finding for the *Execution findings* section, not a task here.
- **A second locale.** §12 is German-only; every key added here is German-only.
