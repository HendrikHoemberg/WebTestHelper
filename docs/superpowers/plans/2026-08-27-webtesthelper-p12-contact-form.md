# WebTestHelper Plan 12 — The Contact Form

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `CONTACT_FORM` — find the form a visitor would actually write in, classify its fields,
fill them plausibly, and then do exactly what the site's owner permitted: nothing, submit, or
submit and prove the message arrived. Plus the two things that setting needs to exist at all: a
verification mailbox in Settings, and `Site.form_test_mode` on a screen.

**Architecture:** the check rides plan 10's machinery. Two new pieces cross a module edge — a
`Mailbox` port in `model` so `checks` can ask "did it arrive?" without seeing `catalog`, and a
per-check timeout on the SPI so a mail round trip is not thrown away by the pass's 30 s budget.
Everything else follows plan 11's D83 unchanged: **the page script harvests, Java decides.**

**Tech Stack:** Java 25, Spring Boot 4.1.1, PostgreSQL 17 via Testcontainers, Playwright/Chromium
1.62.0, Thymeleaf, HTMX, GreenMail 2.1.12 (test). **No new dependency** — measured below.

**Spec:** `docs/superpowers/specs/2026-08-21-webtesthelper-design.md`; §-references point there.
**Roadmap:** `2026-08-27-webtesthelper-phase-3-roadmap.md` — plan 12 of 13. Its deviation index
(D72–D77), plan 10's (D78–D82), plan 11's (D83–D88), the Phase-1 table (D1–D37), plans 6–9's
(D38–D71), `CLAUDE.md`'s plan calibration and `CLAUDE.md`'s test rules all apply and are **not**
restated.

**Ends with:** the failure this product exists to catch. A colleague opens the monthly report and
reads: *"Das Formular auf /kontakt meldet „Vielen Dank“, aber die Nachricht ist nicht im
Prüfpostfach angekommen."* — with the screenshot of the thank-you page that lied. Nobody had to
notice that three weeks of enquiries never arrived.

**One browser test class**, `ContactFormCheckTest`, driving Chromium once per class, plus one
acceptance test. Field classification, form triage, the mode gate and the IMAP poller are all
tested without a browser; the poller's test uses GreenMail and runs under `-Pfast`.

## Measurements taken before this plan was written

The roadmap held two open questions for plan 12 and required both answered by measurement. Both
were measured on 2026-08-27 against real Chromium and a real GreenMail IMAP server. Four more
measurements were taken because writing the plan turned up questions the roadmap had not asked.
**This section is the part of this document that cannot be regenerated by reading the code.**

### Question 1 — no new dependency?

Confirmed. `mvn dependency:tree` shows `org.eclipse.angus:angus-mail:2.0.5` arriving at `runtime`
scope under `spring-boot-starter-mail`, and its jar carries `org/eclipse/angus/mail/imap/` plus the
`META-INF/javamail.providers` entry that registers it. At runtime,
`Session.getProvider("imap")` resolves to
`jakarta.mail.Provider[STORE,imap,org.eclipse.angus.mail.imap.IMAPStore,Oracle]`. The IMAP client
is written against `jakarta.mail` (compile scope) only, so the runtime scope is not a problem.
GreenMail 2.1.12 is already a test dependency and already speaks IMAP. **Nothing is added to
`pom.xml` in this plan.**

### Question 2 — does IMAP verification poll on the run's thread, or resolve later?

**On the run's thread.** Measured against GreenMail, SMTP send → IMAP visibility:

| | run 1 | run 2 | run 3 |
|---|---|---|---|
| SMTP send | 72 ms | 43 ms | 43 ms |
| first IMAP poll (connect + open + search) | 230 ms | 205 ms | 207 ms |
| total, token found on the **first** poll | 303 ms | 249 ms | 251 ms |

And at scale, a mailbox holding 201 messages:

| Operation | Cost |
|---|---|
| connect + `INBOX.open` | 132 ms |
| server-side `BodyTerm` search, exact hit | **54 ms** |
| client-side decode-scan of the **20 newest** messages | **1 649 ms** |

Two decisions fall out. First, a poll cycle costs ~190 ms, so the poll itself is free; what is
being waited on is the customer's mail path, not IMAP. A bounded wait on the run's thread costs one
browser worker up to a minute on the monthly run and buys a finding whose truth is known when it is
written — where deferring means completing a `DEEP` run holding a finding the diff model has no
state for. Second, **search server-side** (D95): the decode-scan is thirty times more expensive
while covering a twenty-message window that a busy mailbox outgrows in an hour.

A subtlety worth recording because it is the opposite of what the encoding suggests: GreenMail's
`BodyTerm` matched a token inside a **base64-encoded `text/html`** part as well as a plain-text
one. IMAP `SEARCH BODY` is specified over the decoded body and Dovecot behaves the same way, so a
token in an HTML-only autoresponder is still findable. The client-side scan is not needed as a
fallback and is not built.

### Question 3 — which field is a trap, and how do you see it?

A honeypot is an input hidden from humans and filled only by bots; filling one makes the site
discard the submission **silently**. The check would then report a healthy form as broken — the
worst false positive in the catalog, because §8 makes the false-positive rate the product. Four
hiding techniques were built and read back through `getBoundingClientRect` plus `getComputedStyle`:

| Technique | rect w×h | rect x | `display` | `visibility` | `opacity` |
|---|---|---|---|---|---|
| `display:none` | 0×0 | 0 | **none** | visible | 1 |
| `position:absolute; left:-9999px` | 185×21 | **−9999** | block | visible | 1 |
| `visibility:hidden` | 185×21 | 461 | inline-block | **hidden** | 1 |
| `opacity:0; height:0` | 177×**0** | 650 | inline-block | visible | **0** |
| `<input type="hidden">` | 0×0 | 0 | none | visible | 1 |
| an ordinary visible field | 185×21 | 46 | inline-block | visible | 1 |

**A rect-only test — the one `clickables.js` and `locale-links.js` use — catches two of the five.**
The offscreen and the `visibility:hidden` honeypots both report a full-size box. So this check reads
five signals, not one, and the rule is geometric rather than lexical (D91): the measured names were
`website`, `fax`, `url2`, `company2`, and a name-based rule would refuse to fill a real *Firma*
field on the next site.

The `<input type="hidden" name="csrf">` in the same form arrived at the server unchanged
(`…&csrf=abc123`) after a pass that left every hidden field alone. Hidden fields are not to be
cleared either — only skipped.

### Question 4 — what does §7.2's "valid input is accepted and invalid input rejected" cost?

Nothing, and no heuristic: the browser answers both.

| Probe | Result |
|---|---|
| plausible values in all seven visible fields, then `form.checkValidity()` | `true`, no invalid element |
| `email.value = "kein-at-zeichen"`, then `checkValidity()` | form `false`, field `false`, `validity.typeMismatch` `true` |
| `<select required>` whose only `<option>` has `value=""` | `validity.valueMissing` `true`, form can **never** validate |
| the same `<select>` after a real option is added and chosen | `true` |

The third row is this plan's `rejectsValid` fixture, and it is a real CMS failure rather than an
invented one: a "Thema" dropdown whose options were never configured. A visitor cannot send the
form and gets no explanation.

### Question 5 — how long does the browser half take, and what does success look like?

| Step | Cost |
|---|---|
| filling seven fields (`fill` ×5, `selectOption`, `check`) | 54 ms |
| submit + navigation to the thank-you page | 50 ms |
| in-page submit (`preventDefault`, DOM replaced) + 500 ms settle | 557 ms |

So the browser half of this check is about **one second**, and the mail wait is everything. Two
success shapes were measured and both must be recognised:

- **navigating**: `page.url()` moves to `/absenden`, title *"Danke"*, body gains *"Vielen Dank … erfolgreich versendet"*.
- **in place**: URL unchanged, the `<form>` element is **gone** (`locator("#f").count() == 0`), body gains *"Danke, Ihre Nachricht wurde gesendet."*

Neither "the URL changed" nor "the form disappeared" is sufficient alone — an error page also
navigates, and a form can be replaced by an error box. The verdict needs both a structural change
**and** the German vocabulary of Task 4.

### Question 6 — which form on the page is the contact form?

Five forms on one page, read through one `evaluate`:

| `id` | `role` | textareas | password | search | captcha marker | verdict |
|---|---|---|---|---|---|---|
| `suche` | search | 0 | 0 | **1** | no | search — skip |
| `newsletter` | — | 0 | 0 | 0 | no | newsletter (one email, no textarea) — skip |
| `login` | — | 0 | **1** | 0 | no | login — **never** submit |
| `kaputt` | — | **1** | 0 | 0 | no | **the contact form** |
| `captcha` | — | 1 | 0 | 0 | **yes** | contact form behind a captcha — abstain |

The captcha marker is one selector,
`.g-recaptcha, [data-sitekey], iframe[src*="recaptcha"], iframe[src*="hcaptcha"], .cf-turnstile, .h-captcha`,
and it matched the reCAPTCHA container. **This one is a convention, not a measurement** — it was
read against a hand-built marker, not against Google's real widget, which the fixture cannot host.
Said plainly so a reviewer does not read it as verified: what is measured is that the selector
finds the container a captcha script replaces, which is what every one of those products documents.

## Deviations this plan introduces

D72–D77 are the roadmap's, D78–D82 plan 10's, D83–D88 plan 11's; each carries its reasoning there.

- **D89 — `Mailbox` is a port in `model`, and its third answer is `UNAVAILABLE`.** `checks` cannot
  see `catalog`, so the check asks an interface and `runner` supplies the IMAP client. The answer is
  three-valued on purpose: a mailbox we could not reach is not a form that does not deliver, and
  collapsing those two into one boolean would let a wrong IMAP password generate an `ERROR` finding
  against a customer's working contact form every month. `UNAVAILABLE` becomes an abstention (D86)
  and a log line, never a finding.
- **D90 — a site configured to submit is checked only on the monthly `DEEP` run; on `FULL` the
  check abstains rather than quietly downgrading to `NO_SUBMIT`.** This is the correctness
  deviation of this plan and it is not obvious. §9 already says submission is a `DEEP` activity, so
  a `FULL` run cannot submit; the tempting move is to run the validation half anyway. But
  `RESOLVE_INTERACTION_SQL` resolves by *(type, page)* and knows nothing about which question was
  asked — so a `FULL` run that answered the *cheap* question on `/kontakt` would mark last month's
  `notDelivered` on `/kontakt` **fixed**, and the next `DEEP` would report it **regressed**. Every
  month, forever: §6.4's motivating failure, one level deeper than D74 found it. Abstaining costs a
  submit-mode site its weekly validation check and keeps its monthly delivery check truthful. A
  site left on the default `NO_SUBMIT` is unaffected and runs every week.
- **D91 — geometry decides what a honeypot is, never the field name.** Measured in Question 3: the
  four traps were named `website`, `fax`, `url2` and `company2`, all of which are legitimate field
  names on some other site. Five signals — `type=hidden`, `display:none`, `visibility:hidden`,
  `opacity < 0.1`, a zero-area or off-viewport rect — and a field tripping any of them is skipped.
- **D92 — `InteractionCheck` gains `default Duration timeout()`, returning `null` for "use the
  pass default".** `CONTACT_FORM` returns 90 s. Without this the runner's existing guard does the
  most damaging thing available: it *discards the findings* of a check that ran long, so the one
  check whose honest runtime is a minute would report nothing and silently narrow coverage. One
  default method, one `if` in the runner, one test.
- **D93 — the verification mailbox is global, the mode is per site, and the copy says what the
  customer has to do.** §4 settled it: *"Not every client will permit a BCC."* Verification works
  only where the customer's form BCCs our mailbox, so the site screen states that in German at the
  point of decision (§13.4) rather than leaving a colleague to discover it from a month of
  `notDelivered` findings against a form that works.
- **D94 — `CONTACT_FORM` ships on, at `ERROR`, in `NO_SUBMIT`.** §1 lists failing contact forms
  among the seven manual checks and §11.1 notifies on `ERROR` only, so `WARN` would mean the product
  quietly stops reporting what it was built for. Default-on is safe **because** the default mode has
  no side effect — which is exactly the reasoning §4 gives for making `NO_SUBMIT` the default.
- **D95 — the token is found by server-side IMAP `SEARCH BODY`, not by fetching and decoding.**
  Measured at 54 ms against 1 649 ms for a twenty-message window (Question 2).

## Decided constants

| Constant | Value | Why |
|---|---|---|
| mail wait budget | 60 s | The poll is free (~190 ms); this is patience with the customer's mail path |
| poll schedule | 0, 3, 8, 15, 25, 40, 60 s | Seven polls ≈ 1.4 s of IMAP work. The measured local case hits on the first |
| `CONTACT_FORM` check timeout (D92) | 90 s | 60 s of mail wait, ~1 s of browser (Question 5), and slack for a slow relay handshake |
| settle wait after submit | 500 ms | Plan 11's measured number, re-confirmed on the in-place submit in Question 5 |
| honeypot opacity cutoff | < 0.1 | `opacity:0` measured; the cutoff is not on a boundary anything real sits near |
| `maxTargets` | 3, unchanged | `webtesthelper.checks.interaction.max-targets`. Three form pages per site |
| token shape | `WTH-` + 12 base32 chars | Long enough that a `SEARCH BODY` hit is the message we sent, short enough to read aloud |

`maxTargets` aside, every number reaches the check through `CheckConfig.option`, per-site
overridable. **No new `@ConfigurationProperties`.**

### Task 1: `ContactForms` — which form, which field, and which one is a trap

The entire judgement half, with no browser near it: pick the form a visitor would write in, decide
what each field is, refuse the traps, and produce a plausible value for each. It is one class
because it is one decision in four parts, and a reviewer cannot accept the classification while
rejecting the honeypot rule that decides which fields get classified at all.

**Files:**
- Create: `checks/ContactForms.java`
- Test: `checks/ContactFormsTest.java`

**Interfaces (produces):**

```java
public record HarvestedField(int index, String tag, String type, String name, String id,
                             String label, String placeholder, String autocomplete,
                             boolean required, String display, String visibility, double opacity,
                             int width, int height, int x, int y, List<String> optionValues) {}
public record HarvestedForm(int index, String id, String action, String method, String role,
                            boolean captcha, List<HarvestedField> fields) {}
public enum FieldKind { EMAIL, NAME, PHONE, SUBJECT, MESSAGE, COMPANY, ADDRESS, CHOICE,
                        CONSENT, SUBMIT, SKIP }
public record ClassifiedField(HarvestedField field, FieldKind kind) {}
public enum FormVerdict { CONTACT, SEARCH, NEWSLETTER, LOGIN, CAPTCHA, NONE }
```

- `static FormVerdict triage(HarvestedForm form)`
- `static Optional<HarvestedForm> choose(List<HarvestedForm> forms)` — the first form triaging
  `CONTACT`, in document order; `CAPTCHA` is remembered by the caller and is not a `CONTACT`
- `static boolean hidden(HarvestedField field, int viewportWidth)` — D91's five signals
- `static List<ClassifiedField> classify(HarvestedForm form, int viewportWidth)`
- `static String plausible(ClassifiedField field, String email, String token)`

**Triage**, first match wins:

1. a `<input type="password">` → `LOGIN`. Nothing else about the form matters; this one must never
   be filled or submitted, and it is checked first for that reason.
2. `role="search"`, or a `<input type="search">`, or an `action` containing `such` or `search`
   → `SEARCH`.
3. the captcha selector matched (harvested as `captcha`) → `CAPTCHA`.
4. no `<textarea>` and at most one non-submit field → `NEWSLETTER`. A newsletter box is one email
   input; a contact form is not.
5. at least one `<textarea>`, or at least three fillable non-hidden fields → `CONTACT`.
6. otherwise `NONE`.

`viewportWidth` is the runner's own `1366` (`InteractionRunner.driveTarget` sets the context
viewport to 1366×900); it is a parameter rather than a constant so the honeypot rule is testable
without knowing what the runner chose.

**`hidden`** is D91: true when `type` is `hidden`, or `display` is `none`, or `visibility` is not
`visible`, or `opacity < 0.1`, or `width == 0`, or `height == 0`, or `x + width < 0`, or `y +
height < 0`, or `x > viewportWidth`. The measured table in Question 3 is the test's oracle, row for
row.

**Classification** reads four sources in this order, first hit wins, all comparisons folded
(lowercase, diacritics stripped — reuse plan 11's folding, do not write a second one):
`autocomplete`, then `type`, then `name` + `id`, then `label` + `placeholder`.

| Kind | `autocomplete` | `type` | words in name/id/label |
|---|---|---|---|
| `EMAIL` | `email` | `email` | `mail`, `email`, `e-mail` |
| `PHONE` | `tel` | `tel` | `telefon`, `phone`, `tel`, `mobil` |
| `NAME` | `name`, `given-name`, `family-name` | — | `name`, `vorname`, `nachname` |
| `COMPANY` | `organization` | — | `firma`, `unternehmen`, `company` |
| `ADDRESS` | `street-address`, `postal-code`, `address-level2` | — | `strasse`, `plz`, `ort`, `adresse` |
| `SUBJECT` | — | — | `betreff`, `subject`, `thema` (on a text input) |
| `MESSAGE` | — | `textarea` | `nachricht`, `message`, `anliegen`, `kommentar` |
| `CHOICE` | — | `select`, `radio` | — |
| `CONSENT` | — | `checkbox` | — |
| `SUBMIT` | — | `submit`, `button`, `image`, `reset` | — |
| `SKIP` | — | anything `hidden(...)` says is hidden, or a `file` input | — |

A `file` input is `SKIP` and never filled: §10.5 puts uploads out of scope for the recorder and
the same reasoning holds here — a check that attaches a file to a customer's contact form is
doing something nobody asked for.

**Plausible values.** German, obviously a test, and stable across runs so a form's own duplicate
detection does not start rejecting the second submission:

| Kind | Value |
|---|---|
| `EMAIL` | the `email` argument (Task 6's mailbox address, or the SMTP from-address) |
| `NAME` | `WebTestHelper Prüfung` |
| `PHONE` | `030 123456789` |
| `COMPANY` | `WebTestHelper (Testeintrag)` |
| `ADDRESS` | `Teststraße 1` / `10115` / `Berlin`, chosen by the matched word |
| `SUBJECT` | `Automatische Prüfung – bitte ignorieren` |
| `MESSAGE` | `Dies ist eine automatische Testnachricht von WebTestHelper. Bitte ignorieren. Kennung: {token}` |
| `CHOICE` | the first `optionValues` entry that is not blank; none → the field is unfillable |
| `CONSENT` | checked |

- [ ] **Step 1: Write the failing test.** `ContactFormsTest`, hand-built records, `-Pfast`.

### Task 2: The mode a colleague picks, from the screen to the check

`Site.form_test_mode` has existed since `V2__site.sql` and `FormTestMode` since Phase 1. Nothing
reads it, nothing writes it, `SiteContext` does not carry it. This task is the whole path — screen,
form model, service, context — plus the scope rule the check will consult. **No check yet**, and
that is the review gate: a reviewer can accept the setting reaching the run and still reject
everything the check does with it.

**Files:**
- Modify: `model/SiteContext.java`, `model/FormTestMode.java`, `catalog/SiteForm.java`,
  `catalog/SiteService.java`, `web/SiteFormModel.java`, `web/SiteController.java`,
  `src/main/resources/templates/websites/formular.html`,
  `src/main/resources/messages.properties`
- Test: `model/FormTestModeTest.java` (create), `catalog/SiteServiceTest.java` (modify),
  `web/SiteControllerTest.java` (modify)

**Interfaces (produces):**
- `SiteContext` gains a trailing `FormTestMode formTestMode` component, with a secondary
  constructor at the current arity defaulting to `NO_SUBMIT` — the shape `SiteForm` already uses
  for `pinnedKeyPages`, and what keeps 34 test construction sites untouched.
- `SiteForm` gains `FormTestMode formTestMode`, same treatment.
- `FormTestMode.submits()` — `this != NO_SUBMIT`.
- `FormTestMode.effectiveFor(RunScope scope)` — returns `this` when `scope == DEEP`, otherwise
  `NO_SUBMIT` when `this == NO_SUBMIT`, otherwise **`null`**, meaning *"this run must not judge
  this form at all"* (D90). Returning `null` rather than a fourth enum constant keeps the
  persisted enum exactly the three values §7.2 names; the check turns `null` into an abstention.
- `SiteFormModel` gains `String formTestMode` bound to a `<select>`.

The screen. One `<select>` in `websites/formular.html` with the three modes, and directly beneath
it the §13.4 consequence sentence, which changes with the selection (Alpine, per §12's division —
this is local state that never touches the server):

| Key | Text |
|---|---|
| `ui.websites.formular.formTestMode` | Kontaktformular-Prüfung |
| `ui.websites.formular.formTestMode.NO_SUBMIT` | Nur ausfüllen, nicht absenden |
| `ui.websites.formular.formTestMode.SUBMIT` | Ausfüllen und absenden |
| `ui.websites.formular.formTestMode.SUBMIT_AND_VERIFY_MAIL` | Absenden und Zustellung im Prüfpostfach nachweisen |
| `ui.websites.formular.formTestMode.folge.NO_SUBMIT` | Es wird nichts abgeschickt. Diese Prüfung hat keine Auswirkung auf den Kunden. |
| `ui.websites.formular.formTestMode.folge.SUBMIT` | Dies verschickt beim Monatslauf eine als Test gekennzeichnete Nachricht über das Kontaktformular dieser Website. Sie landet im Postfach, das dieses Formular bedient. |

measured cost of reconnecting is 132 ms.

when the budget is spent with no hit. `UNAVAILABLE` when the mailbox is not `configured()`, or when

## Deliberately not in this plan

- **The credential store.** Plan 13, and it shares nothing with this plan but `SecretBox`, which
  already exists. No contact-form field reads a credential; a form behind a login is a `LOGIN`
  triage in Task 1 and is never touched.
- **Subject-aware resolution.** D90 works around `RESOLVE_INTERACTION_SQL` being subject-agnostic
  rather than fixing it. Making resolution key on `(check_type, location_key, subject_key)` would
  change the semantics of all sixteen checks and every existing finding row, and it would need its
  own measurement of what it does to the current diff. It is a plan, not a task.
- **Re-verifying a contact-form finding.** The roadmap already states the consequence: re-running
  `CONTACT_FORM` in a submit mode would send a **second** test mail to a customer. The retries live
  inside the check.
- **Solving a captcha, or any form behind one.** Abstention is the honest answer and Task 3 makes
  it. A site whose contact form is behind reCAPTCHA needs a Phase 4 journey with a credential, not
  a heuristic.
- **Multi-step and JavaScript-wizard forms.** One `<form>`, one submit, one outcome. A two-page
  form reads as `NO_INDICATOR` on step one, which is a wrong answer — so if the fixture or a real
  site turns one up, that is a `Deliberately not` item to widen in a later plan, not something to
  patch into `verdict`.
- **File uploads.** A `file` input is `SKIP`, for §10.5's reason.
- **The second `SUBMIT`-mode subtlety: duplicate-submission protection.** A site that rejects the
  second identical message within an hour would report `noSuccess` on a re-run. The plausible values
  are deliberately stable so this is *reproducible* rather than intermittent, and the token differs
  every time, but no fixture proves it. Worth a measurement against a real customer site before
  anyone trusts a same-day re-run.
- **The SMTP relay question of §16.** This plan answers only the mailbox half. The relay, and §16's
  application image, stay open.
- **Any change to the ten page checks or three site checks.** None of them moves.
- **A second locale.** §12 is German-only; every key added here is German-only.

## Execution findings

- **Word-Boundary Matching in Field Classification:** In `ContactForms.java`, field matching was refined to use word/token boundaries with camelCase and delimiter splitting rather than unanchored substring containment, preventing false-positive classifications on tokens like `"ort"`, `"tel"`, and `"mail"` embedded in words like `"support"`, `"antwort"`, or `"hotel"`.
- **Suite Growth & Timing:** Total test suite increased from 1048 to 1140 tests (+92 tests across unit, browser, and acceptance tests; 1137 at first execution, plus the three that the review below added). Full suite wall time is 4m25s (+1m35s over Plan 11 baseline: ~60s is the intentional non-delivery mailbox timeout in Run 1 of `ContactFormAcceptanceTest`, ~35s is Playwright/Chromium execution across contact form test scenarios). All 1140 tests passing with 0 failures and 0 errors.

- **`acceptsInvalid` returned early and cost the site its submit branch.** The first
  implementation returned the `acceptsInvalid` finding instead of collecting it, so
  `if (effectiveMode.submits())` was unreachable for any form whose e-mail field is a plain
  `<input type="text" name="email" required>` — the very shape the plan names as the common German
  case. A site in `SUBMIT_AND_VERIFY_MAIL` therefore got a `WARN` about lax validation *instead of*
  the delivery proof, and §7.2's "only mode that catches the most common real failure" was silently
  off for exactly that class of site. The check now accumulates: `acceptsInvalid` at `WARN` and
  `notDelivered` at the site's severity are two findings about two faults and are reported together.
  `rejectsValid` keeps its early return, and now says why in a comment — a form the browser will not
  let a visitor send cannot be submitted, so pressing the button would only restate the same fault.
  The bug survived the plan because **no fixture had a lax e-mail field**: every form in the suite
  used `type=email`, so `checkValidity()` went false and the branch never ran. `acceptsInvalid`
  appeared in exactly one test line, the `messageKeys()` assertion, and spec §7.2's *"invalid input
  rejected"* had no proof anywhere. `interaktiv/formular-lax-email.html` is that missing fixture.
- **The e-mail typed into the form was a fictional address outside `SUBMIT_AND_VERIFY_MAIL`.**
  `pruefung@webtesthelper.invalid` was hardcoded for `NO_SUBMIT` and `SUBMIT`, against the plan's
  "the mailbox address, or the SMTP from-address". In `SUBMIT` that posts an unreachable address
  into a customer's live form, so nobody can reply to the test message, and a server-side validator
  that rejects `.invalid` turns a healthy form into an `errorShown`. `mailbox.address()` is
  available in every mode and is now used whenever it is non-blank; the constant survives only as
  the no-mailbox fallback. `SUBMIT_AND_VERIFY_MAIL` still abstains up front when it is blank.
- **`triage`/`choose` hardcoded the 1366 viewport** that `hidden` and `classify` take as a
  parameter, defeating the reason the plan gave for the parameter. Both now take it and the check
  passes the context's real width.
- **`SUCCESS_WORDS` was duplicated** verbatim in `ContactForms` and `ContactFormCheck`. It is now
  package-private on `ContactForms` and read from there by `extractSuccessText`.
