# WebTestHelper Plan 13 — The Credential Store

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a per-site store for the one kind of data this system has so far refused to hold — a
password belonging to a customer. Stored with AES-GCM through the `SecretBox` that already
encrypts the SMTP and IMAP passwords, referenced from a step value as `{{cred.login.password}}`,
resolved into a type that cannot be logged by accident, and scrubbed out of any text that echoes
it back.

**Architecture:** four small pieces in `catalog`, in dependency order — a table and a service whose
public record has no password component; a reference parser and a resolver returning `SecretText`
rather than `String`; a value-based `Redactor`; a panel on the site detail screen. Nothing in
`checks` or `runner` changes, no browser is involved, and no check reads a credential.

**Tech Stack:** Java 25, Spring Boot 4.1.1, PostgreSQL 17 via Testcontainers, Thymeleaf, HTMX.
**No new dependency**: `SecretBox` (AES-256-GCM, `/data/keyfile`) has existed since Phase 1 and
Logback's `ListAppender` — the one test tool this plan needs that the suite has not used yet —
arrives with `spring-boot-starter-logging`.

**Spec:** `docs/superpowers/specs/2026-08-21-webtesthelper-design.md`; §-references point there.
**Roadmap:** `2026-08-27-webtesthelper-phase-3-roadmap.md` — plan 13 of 13, the last of Phase 3.
Its deviation index (D72–D77), plan 10's (D78–D82), plan 11's (D83–D88), plan 12's (D89–D95), the
Phase-1 table (D1–D37), plans 6–9's (D38–D71), `CLAUDE.md`'s plan calibration and `CLAUDE.md`'s
test rules all apply and are **not** restated.

**Ends with:** a colleague opens a site, types the password to the customer's CMS once, and never
sees it again. A Phase 4 journey step reads `{{cred.login.password}}`; the run log for that step
reads `FILL benutzer-passwort = {{cred.login.password}}`; and when the login page shouts the
password back in an error message, the finding's evidence reads `Passwort •••••• ist falsch`.

**No browser test, and that is not a lapse.** The roadmap says Phase 3 adds browser tests because
§5.2 makes interaction checks untestable without one. This plan drives nothing: every one of its
deliverables is a pure function or a database round trip, and all its tests run under `-Pfast`.

**No consumer ships here either, and that is the roadmap's design, not an oversight.** Nothing in
Phase 3 reads a credential; §17 places the store in this phase so Phase 4's recorder — §10.5's
*"most likely to consume disproportionate time"* — does not also have to build a secret store on
its first day. Task 5's acceptance test is therefore the first consumer, and it is written as the
journey step that does not exist yet.

## Measurements taken before this plan was written

The roadmap held one open question for plan 13. It is answered below, from evidence rather than
taste, and four more measurements were taken because writing the plan raised questions the
roadmap had not asked. **This section is the part of this document that cannot be regenerated by
reading the code.**

### Question 1 — does a credential belong to a site, or can it be global?

**Per site, `NOT NULL`, `ON DELETE CASCADE`.** The roadmap asked for Phase 4's step model to be
checked before the foreign key is committed. It was, and the step model settles it three times
over:

- §6.1 hangs `Credential` off `Site`, and hangs `Journey` off `Site` too. A step therefore always
  resolves inside exactly one site — there is no context in which the scope is ambiguous.
- §10.4 says *"an encrypted **per-site** store"* in as many words.
- §10.3's reference syntax is `{{cred.<name>.<field>}}` and carries **no site qualifier**. A
  global scope would need a precedence rule between a site's `login` and a global `login`, and a
  journey copied from one site to another would then silently authenticate as a different account.
  That is a security bug with no error message.

What global scope would buy is typing a shared SSO password twice for a client who has two
websites. What it costs is the ambiguity above. **The extension path, if a client ever has six:**
`ALTER TABLE credential ALTER COLUMN site_id DROP NOT NULL` plus one resolution rule (site row
first, global row second). Nothing in this plan's API changes for it.

### Question 2 — what does `SecretBox` actually do, and what does it cost?

Measured against the class in the tree, two boxes over two temporary key directories:

| | Result |
|---|---|
| same plaintext encrypted twice, same key | **different ciphertext** (random 12-byte IV per call) |
| ciphertext length | 48 base64 chars for an 8-char secret, 76 for a 27-char one |
| encrypt | 13.3 µs/op (n = 2000) |
| decrypt | 4.8 µs/op (n = 2000) |
| keyfile | 32 bytes, `rw-------` |

Two consequences. **The ciphertext is not comparable**, so uniqueness, change detection and
"is this the same password" can never be answered in SQL — every such question is a decrypt. And
**a decrypt is free**: 4.8 µs means the screen may probe every stored credential on every render
(Question 3) and resolution may decrypt per step without a cache. There is no caching in this
plan, and that is a measurement, not a preference.

### Question 3 — what happens when the keyfile is lost or replaced?

The failure mode nobody plans for, measured because a store that dies on the day a container is
redeployed with a fresh volume is worse than no store:

| Input to `decrypt` | Result |
|---|---|
| ciphertext from a different key | `IllegalStateException: Decryption failed`, cause `javax.crypto.AEADBadTagException` |
| `"not-base64!!"` | `IllegalArgumentException: Illegal base64 character 2d` |
| `""` or `"AAAA"` | `IllegalArgumentException: Ciphertext too short` |

Note the two different exception types: `decrypt` catches `GeneralSecurityException` only, so
malformed input escapes as `IllegalArgumentException` from the Base64 decoder, before any crypto
runs. Anything that probes readability must catch **both**. This is D101, and it is why the list
screen never decrypts to render a row.

### Question 4 — can redaction use a minimum secret length as a safety cutoff?

**No, and the measurement is unambiguous.** The corpus is everything an interaction run could
plausibly log or store as evidence: the 26 566 characters of the fixture site plus the 37 272
characters of the app's own German UI copy.

| Candidate secret | Length | Occurrences in the corpus |
|---|---|---|
| `web` | 3 | 95 |
| `form` | 4 | 97 |
| `seite` | 5 | 36 |
| `passwort` | 8 | 6 |
| `test` | 4 | 14 |
| `geheim` | 6 | 2 |
| `Sommer26` | 8 | 0 |
| `start123` | 8 | 0 |
| `Kunde2026` | 9 | 0 |
| `Sommer2026!` | 11 | 0 |

Length does not separate the two columns — **dictionary-ness does**, and there is no cheap test
for it. `passwort` and `Sommer26` are the same length and behave oppositely. A length floor would
therefore buy nothing and would cost exactly the wrong thing: it would leave short secrets
unredacted, which is the only failure direction that matters. Over-redaction makes a log line
noisy; under-redaction puts a customer's password in it. **D100 redacts unconditionally.**

The one length that is genuinely dangerous is zero: redacting `""` would insert the mask between
every pair of characters in every string. Blank and whitespace-only secrets are skipped, and that
is the edge case Task 3's test exists for.

### Question 5 — the baseline

`main` at `f60e59b`, both profiles run 2026-08-27, both green:

| | Tests | Classes | Wall time |
|---|---|---|---|
| `./mvnw test -Pfast` | 1005 | 143 | ~1m |
| `./mvnw test` (the pre-merge gate) | **1140** | 159 | 4m27s |

Every test this plan adds runs in the fast profile, so the 135-test gap between the two does not

## Deviations this plan introduces

D72–D77 are the roadmap's, D78–D82 plan 10's, D83–D88 plan 11's, D89–D95 plan 12's; each carries
its reasoning there.

- **D96 — a credential belongs to exactly one site: `site_id BIGINT NOT NULL REFERENCES site (id)
  ON DELETE CASCADE`.** Question 1's answer, and it closes the roadmap's open question for this
  plan. Deleting a site destroys its secrets, which is the behaviour a client's offboarding
  requires and the one `notification_recipient` already has.
- **D97 — the username is stored in clear and shown on screen; only the password is encrypted.**
  §10.4's *"never rendered back to the UI"* is about the secret. A store in which nothing is
  visible cannot be operated: a colleague replacing an expired account has to be able to tell
  which account `login` is, and §13 makes the screen explaining itself a build-enforced
  requirement. Encrypting a value we then render back is theatre that costs a decrypt. **The
  store's job is secrets, not form-filling** — anything non-secret a journey needs to type belongs
  in the step JSON, which is also why two fields are enough (D98).
- **D98 — two fields, fixed: `username` and `password`.** §10.3's `{{cred.<name>.<field>}}` reads
  as an open map, and an open map costs a dynamic-row editor, a validation story, and — the part
  that matters — the ability for Phase 4's step editor to offer a **picker** instead of a free-text
  box. With a fixed set, `{{cred.login.pasword}}` is rejected while the colleague is looking at the
  screen; with an open map it is a journey that fails at 03:00 with an empty field. A customer
  number or a TOTP secret is the extension case, and it is in *Deliberately not*.
- **D99 — the name is immutable after creation.** A journey step refers to a credential *by name*;
  renaming one silently breaks every step that points at it, with no error until the next run.
  Rotation edits the value, never the key. The screen says so, in German, next to the field.
- **D100 — resolution returns `SecretText`, never `String`, and redaction is value-based,
  unconditional, and fixed-width.** Two halves of one rule. A `String` password is one careless
  `log.info("filling {}", value)` away from the disk; `SecretText.toString()` returns the
  *template* — `{{cred.login.password}}` — so the accident that would leak it produces the most
  useful log line available instead. And because a page can echo a password back in its own error
  message, type safety alone is not enough: `Redactor` scrubs the plaintext out of arbitrary text
  by value, for every stored secret regardless of length (Question 4), replacing each with a
  **fixed-width** mask so the redaction never reveals how long the secret was.
- **D101 — an unreadable credential is a state on the screen, not an exception.** Question 3
  measured that a replaced keyfile makes every stored secret throw, in two different exception
  types. The list therefore never decrypts to render — `Credential` has no password component to
  render — and `readable` is computed by attempting a decrypt and catching `RuntimeException`, at
  4.8 µs a row. A lost keyfile becomes a red badge the day it happens rather than a cryptic
  journey failure a month later.
- **D102 — resolution lives in `catalog`, and interaction checks therefore cannot use it.**
  `checks` may see `model` only, and resolution needs the store. This is a real boundary, stated
  here so nobody later concludes it is an oversight: a future check that must log in needs a port
  in `model` supplied by `runner`, exactly as plan 12's `Mailbox` is. Phase 4's replay lives in
  `runner`, which may see `catalog` directly, so the recorder needs nothing more than this plan
  ships.

### Task 1: The table, and a store whose public type has no password in it

The foundation, and the one structural idea worth more than the encryption: the record that leaves
this service **has no component that could carry a plaintext password**. Not a masked one, not an
`Optional` — none. Every later leak has to get past the compiler first.

**Files:**
- Create: `src/main/resources/db/migration/V20__credential.sql`
- Create: `catalog/persistence/CredentialEntity.java`, `catalog/persistence/CredentialRepository.java`
- Create: `catalog/Credential.java`, `catalog/CredentialService.java`
- Test: `catalog/CredentialServiceTest.java` (create), `FlywayMigrationTest.java` (modify)

**Interfaces (produces):**

```java
public record Credential(long id, long siteId, String name, String username,
                         Instant updatedAt, boolean readable) { }
```

```java
public long   create(long siteId, String name, String username, String password);
public void   update(long siteId, long credentialId, String username, String password);
public void   delete(long siteId, long credentialId);
public List<Credential> list(long siteId);          // ordered by name
```

`CredentialEntity` is `NotificationRecipientEntity`'s shape with `name`, `username`, `secret`,
`createdAt`, `updatedAt` and `@Version`. `CredentialRepository extends JpaRepository<…, Long>`
with `findBySiteIdOrderByNameAsc` and `existsBySiteIdAndName`.

**Rules, all of them enforced in `CredentialService` and none in the entity:**

- `create` rejects a name failing the pattern (`credential.name.invalid`), a duplicate name for
  the same site (`credential.name.duplicate`), a blank password (`credential.password.blank`) and
  an unknown site (`Site existiert nicht: <id>`, as `RecipientService.add` does). The same name on
  two different sites is legal and must stay legal — D96 means they are different secrets.
- `update` changes the username always and the password **only when the submitted one is
  non-blank** — the `SettingsController` rule, moved down into the service so the screen cannot get
  it wrong. It never touches the name (D99).
- `update` and `delete` both take `siteId` and ignore a row belonging to another site, exactly as
  `RecipientService.remove` does. A guessed id from another customer's site must not be reachable.
- `readable` is computed per row by calling `secretBox.decrypt` inside a `try`/`catch
  (RuntimeException)` and **discarding the result** (D101, Question 3 — both exception types).

**Migration** — the one code block this task earns, because SQL migrations are inlined by
`CLAUDE.md` and because the cascade and the case-folded unique index are the two things a reader
must not re-derive:

```sql
-- Per-site credential store (spec 6.1, 10.4). The secret is AES-GCM ciphertext from SecretBox;
-- every row in that column is encrypted, so no `encrypted` flag is needed. The username is
-- deliberately in clear: the screen must show which account is configured (D97).
CREATE TABLE credential (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    site_id BIGINT NOT NULL REFERENCES site (id) ON DELETE CASCADE,
    name TEXT NOT NULL CHECK (name <> ''),
    username TEXT,
    secret TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    version BIGINT NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX ux_credential_site_name ON credential (site_id, lower(name));
```

### Task 2: `{{cred.login.password}}` — the reference, and the type that cannot be logged

Resolution, and the deliberate choice that a resolved value is **not a `String`**. The type is
what makes the rest of the system safe by default rather than by discipline.

**Files:**
- Create: `catalog/CredentialField.java`, `catalog/CredentialReference.java`, `catalog/SecretText.java`
- Modify: `catalog/CredentialService.java`
- Test: `catalog/CredentialReferenceTest.java` (create), `catalog/CredentialResolutionTest.java` (create)

**Interfaces (consumes):** `CredentialService.list`, `CredentialRepository`, `SecretBox`.

**Interfaces (produces):**

```java
public enum CredentialField { USERNAME, PASSWORD;
    public String token();                       // "username" | "password"
    public static Optional<CredentialField> parse(String token);
}

public record CredentialReference(String name, CredentialField field) {
    public static List<CredentialReference> findAll(String template);   // in order, duplicates kept
    public String token();                       // "{{cred.login.password}}"
}

public final class SecretText {
    public static SecretText plain(String text);
    public static SecretText of(String resolved, String template);
    public String expose();                      // the only way to the plaintext
    public boolean sensitive();
    @Override public String toString();          // the template — never the plaintext
}
```

```java
public SecretText resolve(long siteId, String template);   // on CredentialService
```

**The parse**, the one algorithm here worth writing down because a reader would otherwise invent a
looser one:

```java
// Anchored to the exact §10.3 syntax: no spaces, name lowercase per the decided pattern.
Pattern.compile("\\{\\{cred\\.([a-z][a-z0-9_-]{0,31})\\.(username|password)\\}\\}")
```

**Resolution rules:**

- No reference in the template → `SecretText.plain(template)`, `sensitive() == false`. A step value
  that is ordinary text stays ordinary text and is logged in full.
- One or more references → each replaced by its value, `sensitive() == true`, and `toString()`
  returns **the original template verbatim**. That is D100's payoff: the log line reads
  `FILL benutzer-passwort = {{cred.login.password}}`, which says more than a row of bullets.
- A reference to a name this site does not have → `IllegalArgumentException` carrying
  `credential.reference.unknown` and **the token, never a value**. Phase 4 turns that into a step
  error naming the missing credential.
- A stored secret that will not decrypt (D101) → `IllegalStateException` carrying
  `credential.reference.unreadable` and the token.
- A **malformed** `{{cred…}}` shape — `{{cred.login.pasword}}`, `{{cred.Login.password}}`,
  `{{ cred.login.password }}` — throws `credential.reference.malformed` rather than passing
  through as literal text. Silently typing `{{cred.login.pasword}}` into a customer's login form
  is the worst available outcome and the one a naive implementation produces.
- `null` template → `SecretText.plain(null)`; `expose()` returns `null`. Steps have optional values.

`SecretText` is final, holds two `String`s, and its `equals`/`hashCode` compare the plaintext while
`toString` never touches it. Resolution decrypts on every call — Question 2 priced it at 4.8 µs and
there is no cache.

- [ ] **Step 1: Write the failing tests.** `CredentialReferenceTest` (no Spring, no database):
      `findAll` on a plain string returns empty; on `{{cred.login.password}}` returns one
      reference with the parsed name and field; on `{{cred.login.username}}/{{cred.login.password}}`
      returns two in order; on `{{cred.Login.password}}`, `{{cred.login.pin}}` and
      `{{ cred.login.password }}` returns empty (they are malformed, not references — the resolver,
      not the parser, is what rejects them); `token()` round-trips a reference back to its literal
      form. `CredentialResolutionTest extends AbstractPostgresTest`, `@Transactional`: a plain
      template resolves to itself and is not sensitive; a single reference resolves to the stored
      password and `toString()` equals the template; a mixed template
      `Benutzer {{cred.login.username}} meldet sich an` substitutes only the reference; an unknown
      name, an unreadable secret (store one by writing junk into the `secret` column through
      `JdbcTemplate`) and each malformed shape throw with the three message keys above, and
      **the exception message contains neither the plaintext nor the ciphertext**; `null` resolves
      to a non-sensitive `SecretText` exposing `null`.

- [ ] **Step 2: Run them and watch them fail** —
      `./mvnw test -Pfast -Dtest='CredentialReferenceTest+CredentialResolutionTest'`.

- [ ] **Step 3: Write `CredentialField`, `CredentialReference` and `SecretText`.** Pure types, no
      Spring. This is the step where `toString()` gets written correctly or the plan has failed.

- [ ] **Step 4: Write `CredentialService.resolve`** — find the well-formed references, reject the
      malformed remainder, decrypt what each names, substitute.

- [ ] **Step 5: Run the tests and watch them pass**, then `./mvnw test -Pfast`.

### Task 3: The redactor, for the password the page shouts back at us

Type safety covers what *we* pass around. It does nothing about a login page that renders
*"Passwort geheim123 ist falsch"* into the DOM, which then lands in a finding's evidence and a run
log. That is what this task is for, and it is why redaction is value-based rather than a logging
pattern.

**Files:**
- Create: `catalog/Redactor.java`
- Modify: `catalog/CredentialService.java`
- Test: `catalog/RedactorTest.java` (create)

**Interfaces (consumes):** `CredentialService`, `SecretBox`.

**Interfaces (produces):**

```java
public final class Redactor {
    public static final String MASK = "••••••";
    public static final Redactor NONE;
    public static Redactor of(Collection<String> secrets);
    public String redact(String text);
    public boolean isEmpty();
}

public Redactor redactorFor(long siteId);   // on CredentialService
```

**Rules:**

- Secrets are applied **longest first**, so a password that contains another password is masked
  whole rather than leaving a readable tail.
- Blank and whitespace-only secrets are dropped at construction. Question 4's dangerous case: an
  empty needle would insert the mask between every character of every string.
- Case-sensitive. A password is case-sensitive, and matching loosely would over-redact without
  catching anything a page would realistically echo.
- `null` in, `null` out. No secrets → `NONE`, whose `redact` returns its argument unchanged
  without scanning; `redactorFor` returns `NONE` for a site with no credentials, so the cost on
  the overwhelmingly common site is one map lookup.
- The mask is the constant regardless of the secret's length (D100).
- `redactorFor` decrypts every credential of the site and **skips the unreadable ones** rather than
  throwing: a broken keyfile must not take out the logging path as well.

## Deliberately not in this plan

Named so a reviewer can tell a gap from a decision.

- **Any consumer.** No check, no crawl, no run reads a credential; §17 puts the store one phase in
  front of its first user on purpose. Task 5 is the stand-in.
- **The recorder, journeys, `JourneyStep` and `SELECTOR_DRIFT`.** Phase 4 (§10). This plan builds
  the one thing §10.4 names and nothing else from that section.
- **A third credential field** — a customer number, a TOTP secret, an API key. D98 fixes the set at
  two, and the extension is a new enum constant plus a column, not a redesign. A customer number is
  not a secret and belongs in the step JSON.
- **A global credential scope.** Question 1 answers why, and names the one-line migration that
  would add it if a client ever has six sites behind one SSO.
- **Widening the redactor to the SMTP and IMAP passwords.** They never leave `AppSettings` and are
  never typed into a page, so there is no measured path by which they reach a log line. Holding
  every secret in the application in one in-memory list to defend against a leak nobody has
  observed is the wrong trade.
- **Redacting screenshots and Playwright traces.** A `Redactor` cannot scan a PNG, and §10.4's
  *"screenshot plus trace on failure"* is Phase 4's to solve — with Playwright's `mask` option on
  the input element, which is a replay concern and not a store concern. Worth a measurement in
  front of the Phase 4 plan, exactly as the roadmap asks for the ones it inherited open.
- **Key rotation.** Re-encrypting every stored secret under a new key is an operations feature with
  its own failure modes (a half-rotated store). D101 makes the *consequence* of a lost key visible,
  which is the part a colleague can act on; rotation itself is a plan.
- **An audit trail of who read or changed a credential.** §6.1 has no such entity and §12's two
  roles do not distinguish it. Adding one silently would be scope no one asked for.
- **Any change to the sixteen checks, the crawl, the coverage model or the fixture site.** Nothing
  in this plan touches them, and the fixture gains no page.
- **A second locale.** §12 is German-only; every key added here is German-only.
